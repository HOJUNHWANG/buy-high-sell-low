**확인된 로딩 병목과 변경 순서**

1. **최신 뉴스 조회 인덱스가 없다.** 현재 인덱스는 `(ticker,published_at)`과 `(event_key,published_at)` 등이며 발행일 단독 정렬에 사용할 선두 컬럼 인덱스가 없다. 운영 `EXPLAIN ANALYZE`에서 `ORDER BY published_at DESC LIMIT 240`이 약 11,000행 전체 스캔 + 정렬, 1,424개 버퍼 블록 접근으로 실행됐다. 4회 실행 시간은 927.892 / 1,218.855 / 204.634 / 132.686ms였다. `(published_at DESC,id DESC)` 인덱스를 검토하고 목록 정렬에도 ID 보조 정렬을 적용하는 것이 우선이다. 이후 실제 계획이 인덱스를 사용하고 접근 블록 수가 줄었는지 확인해야 한다. `pg_stat_statements`의 최신 기사 전체 조회 누적 평균도 약 680ms였지만 이 통계는 과거 실행을 포함한다.

2. **공용 데이터가 요청 사이에서 재사용되지 않는다.** `lib/cached-data.ts`의 React `cache()`는 같은 서버 렌더 안에서만 재사용한다. 요청 간 지속 캐시는 아니다. `/stocks`의 `revalidate=300` 선언도 쿠키를 읽는 Supabase 서버 클라이언트의 모든 조회를 자동으로 5분 공유 캐시로 만들지 않는다. 쿠키 없는 공용 조회 클라이언트와 명시적인 서버 데이터 캐시를 두고 뉴스·시세·위젯은 30~60초, 브리프는 수 분 단위부터 검증할 수 있다. 사용자별 요약 열람 권한은 캐시 밖에서 적용하고, 계좌·거래·청산 가격 검증에는 공용 화면 캐시를 사용하지 않는다. 실제 데이터의 `fetched_at`도 보존한다. [React cache](https://react.dev/reference/react/cache), [Next.js 데이터 캐시](https://nextjs.org/docs/app/api-reference/functions/unstable_cache)

3. **회원 화면이 조회를 직렬로 기다린다.** `/news`는 사용자 확인 → 프로필 → 전체 열람 기록 → 뉴스 순서다. 공용 뉴스는 처음부터 시작하고, 확인된 사용자 ID로 프로필과 필요한 열람 기록을 동시에 가져올 수 있다. 종목 페이지도 회원 정보 조회를 병렬화하고, 메타데이터는 종목 이름·현재 시세만 조회하도록 별도 경로를 둔다. 현재 메타데이터 함수가 전체 차트와 뉴스까지 함께 요청한다. 열람 기록은 화면에 필요한 기사 ID 조회와 일일 사용 수 조회로 범위를 제한한다.

4. **인증 조회를 반복한다.** 최종 브라우저 측정에서 홈·뉴스의 `/auth/v1/user` 2회, 종목·모의투자 3회가 관찰됐다. 일부는 연속 실행되며 한 호출이 최대 약 1.4초였다. 서버 코드에도 Proxy·Navbar·page 각각 호출 경로가 있다. 서버는 요청 단위의 검증된 사용자 조회를 공유하고, 브라우저는 공통 인증 상태를 ThemeProvider·UserMenu·Watchlist에서 재사용한다. 권한 검증을 없애는 방식은 제외한다. `getClaims()`의 로컬 검증 이점은 비대칭 서명 키일 때 적용되므로 현재 프로젝트의 실제 키 방식을 확인한 다음 판단해야 한다. [Supabase 인증 메서드](https://supabase.com/docs/guides/auth/server-side/creating-a-client)

5. **모의투자는 청산 요청 후 다른 API를 시작한다.** 느린 회차에서 청산 API가 약 5.975초, 그 뒤 포트폴리오 1.938초와 챌린지 2.791초였다. 단순히 셋을 동시에 호출하면 청산 전 계좌를 보여줄 수 있다. 세션 검증·계좌 초기화·시세 조회를 공유하는 대시보드 응답으로 합치고, 청산 반영 후 계좌를 읽는 순서는 유지해야 한다. 독립적인 읽기 작업만 겹쳐 실행한다.

6. **화면 밖 탐색용 요청이 많다.** 화면 진입 후 1.2초 관찰 구간에 Next.js 프리페치로 15~33개의 추가 fetch 요청이 관찰됐다. 모두 DB 조회라는 뜻은 아니며 일부는 작은 정적 셸이다. 주요 내비게이션의 프리페치는 유지하고, 많은 종목 행과 태그는 포인터 접근·키보드 포커스 때 실행하는 방식을 비교할 수 있다. [Next.js 프리페치 제어](https://nextjs.org/docs/app/guides/prefetching)

전송량보다 서버 대기가 먼저다. 총 JS 수신량은 압축 해제 기준 약 741~945KiB였으며 프리페치로 받은 코드도 포함한다. 차트 라이브러리는 이미 동적 import를 사용하고, 전역 React Query는 검색에서 사용하므로 무조건 제거할 대상으로 보지 않았다. 먼저 위 조회 경로를 줄인 뒤 모바일 CPU·차트 표시 시간·번들별 전송량을 별도 측정하는 편이 타당하다.

**DISK IO와 서버 자원 관찰**

공식 Metrics API의 두 스냅샷 약 171초 구간에서 시스템 볼륨 `nvme0n1`의 I/O busy 시간은 약 42.3%, 데이터 볼륨 `nvme1n1`은 약 0.2%였다. 시스템 볼륨 읽기 약 29.7MiB/s·쓰기 4.4MiB/s, 스왑 입출력 약 1,156/1,118페이지/초가 관찰됐다. 첫 스냅샷의 전체 메모리는 약 408.5MiB, 가용 약 236.8MiB, 스왑 사용 약 634.8MiB다. 계측과 QA 요청이 진행 중이던 구간이며 완전한 무부하 실험은 아니다.

서버 자원과 스왑이 지연 편차에 기여할 가능성을 뒷받침하지만 단독 원인이나 필요한 요금제는 확정할 수 없다. `I/O busy`는 대시보드의 하루 DISK IO 예산 소비율과 다른 지표다. 앱 조회량 개선 이후 같은 방식으로 비교하고, 지속되면 Supabase 리소스·쿼리 지표로 서버 메모리/컴퓨트 적정성을 확인해야 한다. 재시작·요금제 변경은 수행하지 않았다. [Metrics API](https://supabase.com/docs/guides/observability/metrics), [컴퓨트와 디스크](https://supabase.com/docs/guides/platform/compute-and-disk)

**적용 후 검증 기준**

- 기사 210건의 동일 표본을 재평가하되, 원문 발췌 제공률과 검증된 AI 처리율을 따로 보고한다. 원문 수집 실패·유료 제한·검증 실패·예산 미배정을 구분하고, 중요한 기사 표본에서 종목·주체·숫자·부정 표현을 사람이 확인한다.
- 실제 제공처 HTML을 작은 정제 fixture로 보관해 본문 선택자 회귀를 검사한다. 잘린 문장·광고·제목 반복·추천 기사·429·리다이렉트도 포함한다.
- 뉴스 조회 계획의 스캔 행/블록 수와 실행 시간, 공유 캐시 hit/miss, 페이지별 인증·DB 요청 수를 전후 비교한다. 게스트와 로그인 각각 첫 방문·반복 방문·모바일을 구분한다.
- 포트폴리오는 청산 후 잔액·포지션과 원장이 일치하는지 확인한다. 화면 표시를 빠르게 하기 위해 이전 금융 상태를 사용하는 변경은 허용하지 않는다.
- 이번 표본만으로 개선 후 지연이나 성공률을 보장하지 않는다. 인덱스·캐시·수집기 수정 뒤 같은 표본과 조건으로 다시 측정한다.
